# ADR 0064: The worked example is a recording of the platform, not a description of it

- Status: accepted
- Date: 2026-09-17
- Jira: MIZ-94

## Context

A merchant meeting this API for the first time needs one page that goes from nothing to a refunded
payment. The OpenAPI specifications say what every endpoint takes, and say nothing about the order, which
is the part somebody is stuck on at nine in the evening.

The obvious way to write that page is to write it: paste some curl, paste some JSON, explain. That page is
true on the day it is written. Then a field is renamed, a status code changes, an error grows a code — and
the document keeps being the first thing a merchant reads, for a year, being wrong. Every quickstart in
every repository has this failure, and it is invisible: nothing breaks, nobody is told.

The platform already solved the same problem one level down. The specifications are generated from the
code and committed, and a test in each service compares the committed file against what the running
service serves (ADR 0005). What was missing was the same treatment for the prose.

## Decision

**The worked example is generated by running the journey against a real platform, and CI regenerates it
against the stack it starts and fails if it differs.**

- **Every request and response in the document went over the wire.** `scripts/worked-example.sh` registers
  a merchant, signs in, opens the settlement account, creates, authorizes, captures and refunds a payment,
  writing down what it sent and what came back. Nothing in the code blocks is typed by a person.
- **The volatile parts are normalized, and only those**: ids become fixed placeholders, timestamps a fixed
  instant, tokens a placeholder, and the run's own suffix a `1`. Two runs of the script against the same
  platform produce the same file, byte for byte, which is what makes a diff meaningful.
- **`--check` is the point.** CI runs it against the stack it has already started for the smoke check.
  A field renamed without regenerating the document fails the build, in the same way a spec changed
  without exporting it does.
- **It shows the failures, not only the success.** Reusing an idempotency key for a different request, and
  capturing a payment twice, are steps in the document rather than prose, because what a merchant most
  needs to see is what a refusal looks like.
- **Rate limiting is explained rather than provoked.** A hundred requests a second against a laptop proves
  nothing about a deployment. The document quotes the exact problem detail and explains that nothing was
  done, which is the part a client must know to retry safely; the limit itself is tested in
  `MerchantRateLimitTest` and measured under load.
- **The specifications become a site, built in CI and kept as an artifact.** One page per service, and an
  index. Not published: this platform runs on a laptop, and a page presenting itself as a live API
  reference would be the one untrue thing in the repository.

## Evidence

- `./scripts/worked-example.sh` writes `docs/api/worked-example.md` from a real run against the Compose
  stack; run twice, `--check` passes both times, so the document is reproducible rather than merely
  regenerated.
- The document contains a 409 `IDEMPOTENCY_KEY_REUSED`, a 422 on a second capture, and the refund, exactly
  as the platform answered them.
- `./scripts/api-docs.sh` builds all seven specifications and an index; the pages were opened in a browser
  and render with navigation, descriptions and response samples.
- CI runs the check in the smoke job and builds the site in the console job.

## Consequences

- **Changing an API means regenerating this document**, against a running stack, and committing it. That
  is a real cost, and it is the cost of the document being true. The failure message says which command
  to run.
- **The check needs the whole platform.** It cannot run in the unit test job, so it runs where the stack
  already is. A pull request that only touches documentation still waits for the smoke job.
- **Normalization can hide a real change.** If a field's value is a uuid or a timestamp, a change to it is
  invisible to the diff. The shape is still checked; the values that vary between runs cannot be.
- **The document records one path.** Declines, timeouts, held payments and settlement are not in it; they
  are in the specifications, the ADRs and the smoke check. A worked example that covers everything is a
  reference, and a reference is what the reader already has.

## Alternatives

- **Write the example by hand.** Cheaper today, wrong within a month, and wrong in the one document a
  merchant reads first.
- **Generate it from the OpenAPI examples.** They are per endpoint and invented; the order and the real
  ids linking one call to the next are exactly what a quickstart is for.
- **Publish the site to GitHub Pages.** Then the repository has a live-looking API reference for a
  platform that runs on a laptop, and the URL outlives the commit it was built from.
- **Assert the journey in a test instead of writing a document.** The smoke check already does that. It
  proves the platform works; it does not give a merchant something to read.
